# LexPro 已确认业务规则

[English](../BUSINESS_RULES.md)

本文记录最终数据库和前期讨论已经确认的规则。“待确认事项”中的内容必须在实现前由项目负责人确认。

## 用户、组织和权限

- 系统为内部业务系统，不开放公众注册。
- 管理员负责创建账号和重置密码。
- 每个用户只有一个主要组织（`organization_id`）和一个系统角色（`role_id`）。
- 角色通过 `auth_role_permission` 关联权限。
- 被禁用的用户不能登录。
- 密码只保存 BCrypt 哈希，任何 API 都不能返回密码。
- 新建或重置密码至少 12 个字符，必须包含大小写字母、数字和特殊字符，并且不能超过 BCrypt 的 72 字节输入限制。
- 管理员不能禁用自己当前登录的账号。
- 用户名和组织编码均按大小写不敏感方式判定唯一。
- 账号状态、密码或资料发生修改后，修改前签发的 Access Token 失效。

## 案件

- `case_record` 是案件主记录。
- `case_party` 是嫌疑人、被害人、证人和其他参与人的权威数据来源。
- 用户参与案件及其访问级别由 `case_assignment` 表示。
- `ended_at IS NULL` 表示当前有效分配，不再使用 `is_current`。
- 协作共享使用 `COLLABORATOR + access_level`，不增加单独的案件 ACL 表。
- V2 的组合外键用于禁止不同案件的数据错误关联。
- 不直接保存年龄；需要年龄时根据 `birth_date` 计算。

## 卷宗和智能结果

- 文件二进制保存在 PostgreSQL 之外，`evidence_file.file_url` 只保存内部对象 Key 或 URI。
- 数据库已经支持的删除操作使用软删除。
- 解析结果按版本保存，每个文件只能有一个当前解析结果。
- AI 结果在对应表支持的范围内保存模型、提示词、参数、请求 ID、耗时和 Token 信息。
- 原始 AI 输出必须保留；人工确认后的内容单独保存，并记录确认人和确认时间。
- 文档解析和模型调用不能让前端 HTTP 请求长时间阻塞。
- 三项已批准的 AI 处理能力允许将真实案件文本发送给已配置的 DeepSeek 服务。部署时必须显式设置 `LEXPRO_AI_ALLOW_EXTERNAL_CASE_DATA=true`，并继续遵守最小数据范围、访问控制、审计和日志脱敏要求。

## 案卡、报告和推荐

- 案卡字段保存类型化来源、原文、原文位置和置信度。
- 报告按版本保存，重新生成必须创建新版本，不能覆盖历史版本。
- 模板状态按 `DRAFT -> ACTIVE -> DISABLED` 流转，草稿不能直接禁用；启用新版本时，在同一事务中禁用相同模板编码的上一启用版本。已禁用版本不能重新启用。
- 自动报告生成按 `GENERATING -> DRAFT | FAILED` 流转；人工流转为 `DRAFT -> REVIEWING`、`REVIEWING -> DRAFT` 和 `REVIEWING -> FINAL`，定稿后不可修改。
- 送审和退回要求 `REPORT_MANAGE` 加案件 `EDIT`；定稿要求 `REPORT_MANAGE` 加案件 `MANAGE`。
- 模板和报告正文采用有序 `sections` JSON 协议；报告段落编码、标题和顺序必须与模板完全一致。
- 报告引用证据、法律要素和典型案例时使用规范化关系表。
- DOCX/PDF 使用统一司法文书版式，非定稿文件必须显示草稿标记。
- 典型案例与业务案件分离，通过推荐记录和明细建立联系。
- 已确认使用本地 `BAAI/bge-m3`、1024 维和余弦距离；V4 固定两个现有向量列并增加余弦 HNSW 索引，不新增业务表。

## 类案检索边界

- Java 继续负责认证、案件可见范围、权威业务数据、推荐记录持久化和审计。
- Python 负责检索和模型工作：规范化、结构化/全文/向量召回、融合、重排和推荐理由计算。
- Python 只能处理经过 Java 授权的最小数据范围，不能自行授予案件访问权限。
- 推荐结果使用现有推荐表及其支持的元数据字段，保留查询快照、模型和索引相关参数、排序分数及推荐理由。
- 推荐失败不能削弱权限控制，也不能用未审计、不可追溯的输出静默替代正式结果。
- 本地向量生成或向量召回失败时，Python 可以返回明确标记的纯词法降级结果；数据库或服务整体失败时返回错误且不创建推荐批次。
- 典型案例导入以非空 `external_case_id` 保证幂等；Python 负责规范化和向量化，Java 负责全部语料写入和导入审计。

## MCP 访问边界

- 项目集成一个 MCP Server，但它必须复用已批准的应用服务，不能绕过 Java 服务层和案件级权限检查。
- MCP 工具默认只读，通过明确白名单开放，并校验输入、限制输出。
- 每个写操作 MCP 工具都必须单独批准、明确授权，并写入 `operation_log` 审计记录。
- MCP 响应不能暴露密码哈希、身份证件号码原值、内部存储路径、Token、密钥或未授权案件数据。
- MCP 调用必须解析为已认证且有名称的身份：用户绑定工具使用应用用户，获批的服务器间工具使用已注册 `clientId`。匿名调用不能继承任何一种身份或权限。

## 当前不实现的范围

- 公告、日程和通知仍不属于后端范围，M9 仪表盘不再展示这些原型数据。
- 当前不增加任务事件、报告修订、模型调用、用户角色、用户组织或案件 ACL 表。
- `work_task` 表示人工待办，`operation_log` 用于审计和时间线。

## 工作台

- 没有 `CONTENT_MANAGE` 权限的登录用户只能读取 `PUBLISHED` 知识内容；内容管理员可以读取全部状态并新增、编辑内容。
- 新知识内容初始状态为 `DRAFT`，普通编辑不改变状态。
- 人工任务要求 `TASK_MANAGE`；关联案件的任务还必须遵循案件可见范围，新增或编辑时要求案件 `EDIT` 访问级别。
- 人工任务必须且只能关联一个案件或知识内容；新任务初始状态为 `PENDING`，负责人默认为创建人。
- 任务和知识变更写入 `operation_log`，不增加独立任务事件表。

## 待确认事项

- 案件状态允许的完整流转矩阵。
- 知识内容和人工任务的完整状态流转矩阵及授权角色。
- 案件编号的唯一性和生成规则。
- 身份证件号码的加密、查询和脱敏规则。
- 是否需要调整 M4 暂定上传白名单和 25 MB 开发限制，以及文件保留期限。
- 生产对象存储布局、MinIO 部署方式和病毒扫描要求。
- MinerU 服务提供方、生产 AI 超时/并发上限及模型降级策略。
- AI 评估阈值，以及已批准 DeepSeek 外发范围之外的供应商级数据分级和脱敏规则。
- 外部 MCP 服务令牌注册表、首批客户端权限/配额以及具体客户端验收的最终批准。
- MCP 生产网络暴露策略和来源网络策略。
