# LexPro 与 legal_llm 整合及数据迁移施工方案

> 状态：核心方案已确认，执行审批待后续阶段  
> 编制日期：2026-09-03  
> 适用范围：徐老师新版前端、MinerU、LexPro_8B、实体识别与原文定位、典型案例查询、SQLite 数据迁移  
> 本文是施工计划，不代表已批准执行；涉及数据库结构、数据写入、外部 AI 服务和部署的步骤必须在对应审批点确认后实施。

## 1. 建设目标

在保留原 LexPro 正式工程基础的前提下，完成以下四项已确认需求：

1. 系统挂载 LexPro_8B 实体识别模型和 MinerU 文档解析服务。
2. 完善实体识别、结果展示以及识别结果在原文中的定位展示。
3. 采用徐老师在 `legal_llm` 中实现的新版前端页面和交互设计。
4. 典型案例继续使用原 LexPro 接口，将前端改为“选择条件 + 提交表单 + 结果列表”的调用方式。

同时，将 `legal_llm` SQLite 中有价值的数据安全迁移到 LexPro PostgreSQL：迁移 6786 条典型案例，并重建式迁移5个演示案件及其案卷文件；不把演示系统的弱权限、明文密钥、错误实体位置或演示日志带入正式系统。

## 2. 总体结论和施工原则

### 2.1 技术路线

采用“界面迁移、能力接入、正式底座保留”的路线：

```text
徐老师 legal_llm 页面和交互
            │ 迁移/组件化
            ▼
原 LexPro Vue 3 前端
            │ /api/v1
            ▼
原 LexPro Spring Boot 后端
       ┌────┴─────────────┐
       ▼                  ▼
PostgreSQL          Python AI 服务适配层
正式业务数据          ├─ MinerU /parse
权限/版本/审计         └─ LexPro_8B /v1/completions
```

### 2.2 保留、迁移和废弃边界

| 内容 | 处理方式 | 原因 |
|---|---|---|
| 原 Spring Boot 后端 | 保留并扩展 | 权限、案件隔离、任务、版本、审计、错误协议完整 |
| 原 PostgreSQL 数据库 | 保留并按新迁移版本扩展 | 约束、外键、版本管理和可追溯性完整 |
| 原 Vue 3 工程 | 保留作为最终前端载体 | 组件化、路由、权限和构建体系成熟 |
| `legal_llm` 页面设计 | 迁移到 Vue | 新页面视觉和交互更符合本次需求 |
| `legal_llm` Flask 业务后端 | 不作为正式主后端 | 权限、版本、HTTP 状态、安全和测试不足 |
| `legal_llm` SQLite | 只作为迁移源 | 可提取有价值数据，但不作为正式数据库 |
| SQLite 用户、日志、模型密钥 | 不迁移 | 密码体系不兼容、日志不应混入、密钥为明文 |
| SQLite 旧实体结果 | 默认不迁移 | 句内偏移与全文偏移混用，定位结果不可靠 |

### 2.3 不得破坏的基线

1. 不修改已经应用的 V1、V2、V3、V4、V5 SQL；新结构只能增加后续 Flyway 迁移。
2. 不绕过 Spring Boot 服务层的案件权限和数据访问控制。
3. 不将真实案件材料发送到未经批准的外部 AI 服务。
4. 不在代码、SQLite、PostgreSQL或日志中保存明文模型密钥。
5. 所有数据迁移先做只读预览和本地库轻量备份，再按小批到全量的顺序写入本地开发库。
6. SQLite 源文件、原 PostgreSQL 数据和案卷实体文件必须保留可验证备份。

## 3. 当前基线

### 3.1 原 LexPro

- 前端：Vue 3、Vue Router、Element Plus、Vite；正式构建已通过。
- 后端：Java 21、Spring Boot 3.5、MyBatis-Plus；现有 163 个测试全部通过。
- 数据库：PostgreSQL，V1 + V2 + V3 为 32 张业务表，V4/V5补充向量和合作方典型案例字段。
- 已有正式能力：认证、用户、组织、案件、当事人、分配、案卷、解析任务、实体任务、要素任务、摘要、案卡、报告、典型案例、收藏、审计。
- 当前缺口：仅有本地 TXT 解析器；实体识别不是 LexPro_8B；前端没有实体原文定位；典型案例表单没有暴露完整筛选条件。

### 3.2 `legal_llm`

- 前端：纯 HTML/CSS/JavaScript，新版页面和展示较完整。
- 后端：Flask，适合作为原型参考，不作为正式主后端。
- 数据库：SQLite 16 张表；当前 `case_base` 有 6786 条典型案例，实际数量在迁移执行前重新统计。
- 已实现原文高亮界面，但实体偏移量存在句内坐标直接用于全文的错误。
- MinerU 目前是本机 CLI 探测/调用，并非部署说明书中的 HTTP 服务接入。
- 模型使用聊天补全接口，与 LexPro_8B 的批量 `/v1/completions` 合同不一致。

### 4.1 D3 实施说明：只使用新的六类实体

本期 API、前端筛选、颜色图例、统计和人工确认只接受以下六类：犯罪嫌疑人、地名、组织机构名、时间、罪名、毒品种类。

原系统已经生成的 PERSON、DATE、MONEY、CASE_NUMBER、LEGAL_REFERENCE 等旧类别结果不再转换或兼容展示。上线切换时：

1. 不物理删除历史结果，避免未经批准的数据破坏和审计链断裂。
2. 旧结果不得被标记为新的“当前有效结果”，也不得进入新页面统计和下游生成流程。
3. 对仍需使用的历史文档，使用 LexPro_8B 重新执行识别，生成六类实体的新版本。
4. 新接口遇到六类之外的模型输出时按“未知类型”校验失败，不自动归入 `OTHER`。

### 4.2 D6 已确认：迁移典型案例和演示案件

迁移范围包括两部分：

1. **典型案例库**：迁移 `case_base` 中的 6786 条典型案例，以及来源、事实、裁判结果、理由、典型意义等内容。
2. **演示案件**：迁移当前5个演示案件的案件基本信息和实际案卷文件。

演示案件采用“重建式迁移”，而不是复制 SQLite 的全部关联行：

1. 将 SQLite `cases` 转换为原 LexPro 的案件创建请求。
2. 为案件指定原 LexPro 中已经存在的正式测试用户、组织和承办关系；不迁移 Flask 用户密码。
3. 查找 `dossier_files.file_path` 对应的真实文件，校验文件存在、大小和 SHA-256。
4. 通过原 LexPro 案卷上传接口重新上传文件，使存储路径、哈希、权限和审计由正式后端生成。
5. 使用服务器 MinerU 对上传后的文件重新解析。
6. 使用服务器 LexPro_8B 重新生成六类实体。
7. 法律要素、摘要、案卡和报告根据演示需要通过正式流程重新生成。

以下 SQLite 数据仍不直接迁移：

- 4个演示用户及其密码。
- 233条 Flask 操作日志。
- 模型配置和明文 API Key。
- `parsed_docs`、`entity_results`、`element_results`、`summary_results`。
- `push_results`、`card_tasks`、`card_fields` 和 `reports` 的旧运行结果。

这样既能保留5个演示案件和案卷材料，又不会把错误实体 offset、简化权限、旧状态和缺少版本信息的结果带入正式系统。原 SQLite 和文件目录保留为只读核对源，不因迁移而删除。

演示案件迁移的必要前提：

- [ ] 已指定接收这些案件的原 LexPro 测试组织和用户。
- [ ] 5条 `dossier_files` 引用的真实文件全部找到；缺失文件列入清单。
- [ ] SQLite 案件状态到 LexPro 状态的映射已审核。
- [ ] 演示材料确认不包含禁止发送到模型服务的真实敏感数据。

### 4.3 D8 已确认：直接使用本地开发数据库

本地开发 PostgreSQL 没有需要保留的业务数据，因此不再单独搭建隔离测试库。施工直接面向本地开发库，但保留最小安全措施，防止字段映射或脚本错误污染开发环境。

```text
SQLite 源文件
   │
   ├─ 只读预览和转换报告
   │
   ├─ 本地开发 PostgreSQL：应用 V6
   │
   ├─ 先导入10条典型案例 + 1个演示案件验证
   │
   └─ 验证通过后导入剩余典型案例和演示案件

生产 PostgreSQL：本次不连接、不写入
```

直接开发仍保留以下步骤：

1. 开始前记录本地数据库主机、端口、数据库名、Flyway版本和各表行数。
2. 对当前本地库执行一次轻量 `pg_dump`；即使数据无价值，也可快速恢复结构和开发账号配置。
3. 对 SQLite 运行只读预览，先发现非法JSON、日期、重复ID和缺失文件。
4. V6 只能作为新的 Flyway 迁移执行，不修改已经应用的 V1–V5。
5. 先导入10条不同来源的典型案例和1个演示案件，完成接口和页面验证。
6. 小批验证通过后再分批导入剩余数据；每批保留导入清单和 request ID。
7. 导入工具必须显示目标数据库名称，并拒绝连接名称或主机不符合本地开发配置的数据库。
8. 生产环境迁移不属于本次施工，未来上线时另行制定审批和备份步骤。

因为本地库没有有价值的数据，开发阶段出现不可修复的导入错误时，可以清理本批带来源标识的数据；如需删除或重建数据库，仍须在执行前明确确认具体目标，不能对未知数据库执行破坏性命令。

## 7. P1：冻结接口、实体位置和数据映射合同

### 7.1 AI 服务内部接口

建议由独立 Python 服务提供以下内网接口，Spring Boot 是唯一业务调用方：

| 接口 | 用途 | 返回方式 |
|---|---|---|
| `GET /internal/v1/health` | 服务总体健康 | MinerU、LexPro 分项状态，不返回密钥 |
| `GET /internal/v1/readiness` | 是否可接受任务 | 模型加载、依赖和GPU状态 |
| `POST /internal/v1/documents/parse` | 调用 MinerU 解析 | 同步返回中小文件；超时由 Spring 任务记录失败 |
| `POST /internal/v1/entities/recognize` | 调用 LexPro_8B | 接收有序文本块，返回块内实体 |

Python 服务只负责模型适配和输出规范化，不直接连接 LexPro PostgreSQL，不自行决定案件权限，也不保存正式业务结果。

### 7.2 MinerU 解析合同

统一解析结果至少包含：

```json
{
  "schemaVersion": "lexpro.parse.v2",
  "offsetUnit": "UTF16_CODE_UNIT",
  "parser": "mineru",
  "parserVersion": "待联调确认",
  "rawText": "按阅读顺序拼接后的全文",
  "textSha256": "全文哈希",
  "blocks": [
    {
      "blockId": "b-000001",
      "pageNo": 1,
      "order": 1,
      "type": "text",
      "text": "文本块内容",
      "globalStartUtf16": 0,
      "globalEndUtf16": 20
    }
  ]
}
```

约束：

1. `globalStartUtf16` 包含、`globalEndUtf16` 不包含，即 `[start, end)`。
2. `rawText.substring(globalStartUtf16, globalEndUtf16)` 必须等于块文本或等于合同约定的规范化文本。
3. 块按 `pageNo + order` 稳定排序。
4. PDF、PNG、JPG、DOC、DOCX 的失败原因必须返回稳定错误码，不返回服务器绝对路径和堆栈。
5. 不允许 MinerU 失败后静默改用简化解析器；是否允许降级必须由任务参数明确指定，并在结果中记录实际解析器。

### 7.3 LexPro_8B 实体合同

本期六类实体：

| 业务代码 | 中文名 |
|---|---|
| `SUSPECT` | 犯罪嫌疑人 |
| `LOCATION` | 地名 |
| `ORGANIZATION` | 组织机构名 |
| `TIME` | 时间 |
| `CRIME` | 罪名 |
| `DRUG` | 毒品种类 |

规范化后的文档级实体结构：

```json
{
  "schemaVersion": "lexpro.entity.v2",
  "offsetUnit": "UTF16_CODE_UNIT",
  "modelName": "LexPro_8B",
  "modelVersion": "待部署确认",
  "sourceTextSha256": "对应解析全文哈希",
  "entities": [
    {
      "type": "SUSPECT",
      "text": "张某",
      "normalizedText": "张某",
      "globalStartUtf16": 105,
      "globalEndUtf16": 107,
      "blockId": "b-000006",
      "blockStartUtf16": 8,
      "blockEndUtf16": 10,
      "confidence": 0.96
    }
  ],
  "deduplicated": {
    "SUSPECT": ["张某"]
  }
}
```

位置换算规则：

1. LexPro_8B 返回句内或块内位置时，Python 适配层保留原位置和原始位置单位；Spring Boot 根据已保存的块起点换算全文位置。
2. 后端必须验证 `rawText.substring(globalStartUtf16, globalEndUtf16) == text`，验证失败的实体不能作为有效定位结果入库。
3. 同一句中相同文字多次出现时，必须使用模型位置和块位置联合定位，不能只执行第一次字符串搜索。
4. JavaScript 和 Java 使用 UTF-16 code unit 索引；Python 默认使用 Unicode code point。接口必须明确原始位置单位，并由 Java 生成最终 `globalStartUtf16/globalEndUtf16`。
5. 展示去重不能删除原始 occurrence；列表可按实体值聚合，但原文高亮必须保留每一次出现位置。
6. 模型响应越界、文字不匹配、类型未知、JSON非法时，记录稳定错误分类和校验报告。

#### 7.3.1 三个容易混淆的概念

| 概念 | 本系统用途 | 决策 |
|---|---|---|
| UTF-8 字节 | 文件、HTTP和 PostgreSQL 编码 | 继续使用；不用于前端字符串定位 |
| Unicode code point | Python字符串常用下标 | 允许作为模型适配层的原始下标，必须显式声明并换算 |
| UTF-16 code unit | Java `String` 和 JavaScript字符串下标 | 作为最终 API 和数据库实体位置单位 |
| Grapheme cluster | 用户肉眼看到的一个完整字形 | 用于校验不能切断组合字符，不作为持久化数字下标 |

“使用 UTF-16 offset”不表示把文件保存成 UTF-16。文件和网络仍使用 UTF-8；只有实体的数字位置使用与 Java/JavaScript 一致的字符串下标。

#### 7.3.2 唯一权威原文和规范化规则

位置必须绑定到一份确定且不可变的 `canonicalText`，不得同时对 PDF 原始字节、MinerU临时输出、去空格文本和浏览器渲染文本计算同一组 offset。

生成 `canonicalText` 时只允许以下确定性处理：

1. 移除全文开头的单个 BOM `U+FEFF`，正文其他位置的 BOM 不静默删除。
2. 将 `CRLF`、单独 `CR`、Unicode行分隔符 `U+2028` 和段落分隔符 `U+2029` 统一为 `LF`，且必须在计算任何 offset 之前完成。
3. 按 MinerU 的稳定块顺序拼接，块之间固定插入 `\n\n`；块起点在拼接时记录。
4. 除上述规则外，保留空格、制表符、全角空格、不间断空格、标点和换行，不执行 `trim`。
5. 不对权威原文执行 NFC、NFD、NFKC 或 NFKD Unicode 归一化。例如全角数字、兼容汉字、`é` 与 `e + 组合音标`保持原样。
6. 可为检索、去重另建 `normalizedText`，但规范化值不得用于原文高亮 offset。
7. 遇到 NUL `U+0000`、无法解码字节或非预期替换字符 `U+FFFD` 时，不静默吞掉；解析结果标记警告或失败并进入人工检查。

`textSha256` 使用 `canonicalText` 的 UTF-8 字节计算。哈希使用 UTF-8 与位置使用 UTF-16并不冲突：哈希用于证明文本版本，offset用于 Java/JavaScript切片。

#### 7.3.3 Python 到 Java/JavaScript 的位置换算

Python服务返回位置时必须同时返回 `offsetUnit`，允许值仅为：

- `UNICODE_CODE_POINT`
- `UTF16_CODE_UNIT`

不接受未声明单位的裸 `start/end`。如果模型给出的是 Python code point 下标，换算逻辑等价于：

```text
utf16Offset(text, codePointOffset)
  = length(text[0:codePointOffset] 编码为 UTF-16LE) / 2
```

实际实现应对每个文本块预计算 code point → UTF-16 前缀映射，避免对每个实体重复编码。Java接收后必须再次检查：

```text
0 <= start < end <= canonicalText.length()
canonicalText.substring(start, end) == entity.text
start/end 不落在 UTF-16 高低代理项中间
```

任何一项失败均不能进入可点击定位列表。可保留为 `UNLOCATED` 候选供人工查看，但不得伪造位置。

#### 7.3.4 特殊字符处理表

| 特殊情况 | 示例 | 风险 | 处理方式 |
|---|---|---|---|
| 普通中文和英文 | `张某在北京` | UTF-8字节数与字符数不同 | 不使用 UTF-8 字节作为 offset |
| 生僻汉字/扩展区汉字 | `𠮷` | Python算1个 code point，Java/JS算2个 code unit | 使用映射转换并验证代理项边界 |
| Emoji | `😀`、`👍🏽` | 一个视觉符号可能包含2个或更多 UTF-16单元 | 不允许截断代理项或修饰符 |
| 零宽连接 Emoji | `👨‍👩‍👧‍👦` | 一个视觉符号由多个字符和 ZWJ组成 | 原样保留；实体边界不得切断完整字形 |
| 组合音标 | `e\u0301` | 肉眼一个字，实际两个 code point | 不做 NFC/NFD；按原字符串验证 |
| 变体选择符 | `️`、`U+FE0F` | 显示样式字符容易被清理 | 原样保留，不在定位前删除 |
| CRLF/CR/LF | Windows与Linux换行 | 每行之后的位置可能整体偏移 | 在生成权威原文前统一成 LF |
| BOM | 文件开头 `U+FEFF` | 第一个实体整体偏移1位 | 只允许移除开头BOM并记录 |
| Tab | `\t` | 浏览器视觉宽度不等于字符串长度 | 原样保留，使用 `pre-wrap` 展示 |
| 不间断空格 | `U+00A0` | 看似普通空格但不相等 | 不静默替换；必要时仅在 normalizedText处理 |
| 全角空格 | `U+3000` | trim/折叠可能破坏位置 | 权威原文保留 |
| 全角数字和标点 | `１２３，。` | NFKC 会改变文本 | 权威原文不做兼容归一化 |
| PDF连字 | `ﬁ` | 视觉为 `fi`，文本可能是单字符 | 以 MinerU canonicalText 为定位依据 |
| 零宽空格/软连字符 | `U+200B`、`U+00AD` | 肉眼不可见但占字符串位置 | 原样保留并在调试视图中允许显式显示 |
| 双向文本控制符 | `U+202E` 等 | 视觉顺序可能与逻辑字符串顺序不同 | offset按逻辑顺序；标记可疑控制符，前端隔离文本方向 |
| OCR错字 | `北亰` | 与扫描图视觉内容可能不一致 | 文本高亮仍锚定OCR文本；另用页码/bbox定位图像 |
| JSON转义 | `\n`、`\u4e2d` | 序列化表示与运行字符串不同 | offset针对反序列化后的真实字符串 |
| HTML特殊字符 | `<script>`、`&` | `innerHTML`可能注入或改变文本 | 使用文本节点或严格转义后再包裹高亮标签 |
| 重复实体 | 多次出现“张某” | `indexOf`只找到第一次 | 使用块ID、模型位置、上下文和出现序号联合定位 |
| 非法孤立代理项 | 单独 high/low surrogate | Java可暂存但不是合法 Unicode标量 | 解析/接口校验失败，不进入数据库和页面 |

#### 7.3.5 不能只保存 offset：采用复合锚点

每个实体 occurrence 除全文 UTF-16位置外，还应保存或在 JSON 中携带：

- `docId` 和解析版本。
- `sourceTextSha256`。
- `blockId`、`blockTextSha256`。
- `blockStartUtf16`、`blockEndUtf16`。
- `globalStartUtf16`、`globalEndUtf16`。
- 原文 `text`。
- 前后文 `prefix`、`suffix`，建议各取最多16个 Unicode code point。
- 同块同文本的 `occurrenceIndex`。
- 可用时保存 `pageNo` 和 MinerU 返回的 `bbox` 及坐标单位。

验证顺序：

1. 文档哈希和解析版本一致。
2. 块哈希一致。
3. 块内位置能精确切出 `text`。
4. 换算后的全文位置能精确切出同一 `text`。
5. 前后文锚点一致。

若模型位置不准，只允许在声明的同一块及邻近窗口内执行精确重定位。文本在窗口内不唯一或只能通过模糊匹配找到时，标记 `AMBIGUOUS`/`UNLOCATED`，交由人工确认；法律材料不得通过模糊匹配自动制造“精确位置”。

#### 7.3.6 文本定位与 PDF 视觉定位是两层能力

本期必须完成的是文本层定位：点击实体，在 MinerU 权威原文中滚动并高亮。

如果要求在 PDF扫描页或图片上框选实体，仅有字符 offset 不够，还需要 MinerU 为文本块或单词提供：

- `pageNo`
- `bbox = [x0, y0, x1, y1]`
- `coordinateUnit`，例如 PDF point、pixel 或 0–1归一化坐标
- 页面宽高和旋转方向

MinerU没有返回可靠 bbox 时，页面只能跳到对应页并展示文本块，不能伪造精确框选。本期将页码/bbox字段保留为可选合同，真实支持程度在服务器 MinerU联调时确认。

#### 7.3.8 前端渲染规则

1. 不能先把原文转成 HTML 再按 offset切割；必须先对原始 JavaScript字符串按实体边界分段，再创建文本节点和高亮节点。
2. 不使用未转义的 `innerHTML` 拼接案卷原文，防止案卷文字被浏览器解释为标签或脚本。
3. 原文容器使用保留空白的样式，如 `white-space: pre-wrap`；Tab的视觉宽度不影响字符串位置。
4. offset按字符串逻辑顺序，不根据浏览器渲染后的像素位置或 `innerText`重新计算。
5. 处理重叠实体前先定义规则：同范围可合并标签；交叉范围标记冲突，不静默截断。
6. 渲染前检查 surrogate pair边界，不能用 `slice`切开生僻字或Emoji代理对。
7. 对组合字符、变体选择符、Emoji修饰符和 ZWJ序列进行完整字形边界检查；发现实体只覆盖其中一部分时标记校验失败。
8. 双向文本使用隔离显示策略，避免阿拉伯文、希伯来文或控制符影响页面其他区域，但数据顺序保持不变。

### 7.4 前端合同

前端只消费 Spring Boot `/api/v1`，不直接调用 Python 服务。实体页面需要获得：

- 当前解析全文和文本哈希。
- 当前实体结果、历史版本和处理状态。
- 每个实体的全文位置、块位置、类别、置信度和确认状态。
- 可编辑的人工确认结果，且不覆盖原始模型结果。

### 7.5 P1 验收条件

- 四类合同（MinerU、LexPro、Spring API、前端实体模型）均有固定样例。

补充界面规则（2026-09-03，已确认）：

1. 裁判日期只使用一个日期输入框，按单个精确日期查询；不设计起止区间，也不保留“单端表示之前/之后”的交互。
2. 案由、案件类型、来源、案例层级等筛选项只显示名称，不在下拉项或页面统计卡中显示各类别数据条目数。
3. 分页仍可使用后端总数计算页码，但页面不把它包装成某一类别的数量统计。

> 实施进度（2026-09-04）：正式 Vue 推荐页面已接入典型案例库查询、详情和收藏；关键词、案由、案件类型、法院、地区、文书类型、来源、案例层级、单个精确裁判日期和仅收藏筛选均已落地，且不展示类别数量。V6 已备份后应用到本地开发库并通过真实 HTTP 筛选验证。

创建推荐必须满足 `sourceSummaryId` 与 `factText` 二选一，不允许同时为空或同时提交。

### 12.3 后端调整边界

1. 优先扩展现有查询 DTO、Service 和 Mapper，不新建一套推荐接口。
2. 前端不再调用 `legal_llm /casebase` 和 `/analysis/push/recommend`。
3. 保留 LOCAL/PARTNER Provider 选择逻辑和分析令牌验证。
4. 过滤条件必须在服务层校验，不能只依赖前端下拉框。
5. 推荐结果继续保存推荐批次、排名、分数、理由、模型/Provider和请求参数。

### 12.4 验收条件

- 每个表单字段都能在后端请求或查询中产生可验证效果。
- 清空筛选、分页、详情、收藏和历史可用。
- LOCAL 和 PARTNER 模式行为符合现有业务规则，不发生静默切换。
- 普通用户只能为有权访问的案件创建和读取推荐。

## 13. P7：SQLite 典型案例和演示案件迁移

### 13.1 迁移范围

### 13.3 去重和幂等规则

1. 主幂等键：规范化后的 `external_case_id`。
2. 建议格式：`legal_llm:<source>:<caseid>`；当 `caseid` 为空时使用 `legal_llm:sha256:<fingerprint>`。
3. 指纹建议由标题、法院、裁判日期、案由、事实正文规范化后计算。
4. 同一幂等键内容完全相同：标记 `SKIP_IDENTICAL`。
5. 同一幂等键内容不同：标记 `CONFLICT`，不得静默覆盖。
6. 不同ID但标题、法院、日期、事实高度相同：标记 `POSSIBLE_DUPLICATE`，进入人工抽查。
7. 迁移脚本重复运行必须得到相同结果，不能重复插入。

### 13.5 具体执行步骤

#### 第一步：只读预览

1. 打开 SQLite 只读连接。
2. 重新统计 `case_base` 实际行数。
3. 检查空标题、空事实/正文、非法 JSON、非法日期、字段超长。
4. 检查5个演示案件的必填字段、状态、用户引用和案件编号冲突。
5. 检查所有 `dossier_files.file_path` 对应实体文件是否存在并计算哈希。
6. 生成标准化预览，不连接 PostgreSQL写库。
7. 输出接受、警告、拒绝、冲突、可能重复和缺失文件清单。

产出：`preview-summary.json`、`accepted.ndjson`、`warnings.csv`、`rejected.csv`、`duplicates.csv`。

#### 第二步：准备本地开发库

1. 显示并确认本地 PostgreSQL 主机、端口、数据库名和当前 Flyway 版本。
2. 记录迁移前各目标表行数并生成一次轻量 `pg_dump`。
3. 经数据库变更审批后执行 V6 Flyway 迁移并验证约束。
4. 启动 Spring Boot，以专用开发管理员账号获取短期访问令牌。
5. 迁移工具必须拒绝非本地主机或非预期数据库名。

#### 第三步：小批试导与核验

1. 先导入10条覆盖不同来源和字段组合的典型案例。
2. 验证列表、详情、过滤、推荐检索和中文内容。
3. 选择1个演示案件，创建案件、建立承办关系并重新上传实际文件。
4. 对该文件调用服务器 MinerU 和 LexPro_8B，验证解析、六类实体和原文定位。
5. 小批验证失败时停止，不继续导入剩余数据。

核对公式：

```text
源总数 = 接受数 + 警告接受数 + 拒绝数
计划导入数 = 新增数 + 已存在相同数 + 冲突数
目标本批新增数 = 成功返回并通过查询验证的唯一ID数
```

至少执行：

- 总量核对。
- external ID 唯一性核对。
- JSON字段类型核对。
- 日期范围核对。
- 空正文核对。
- 每个来源随机抽样不少于10条。
- 超长正文、中文标点和换行抽样。
- 典型案例列表、详情和推荐接口真实HTTP验证。
- 演示案件详情、承办关系、文件下载和任务历史真实HTTP验证。

#### 第四步：本地开发库全量导入

小批试导通过后：

1. 冻结 SQLite 源文件并复核哈希。
2. 分批导入剩余典型案例；任何冲突率或失败率超过阈值立即停止。
3. 逐个重建剩余演示案件，并通过正式上传接口导入文件。
4. 逐个验证案件权限、文件哈希和下载内容。
5. 按演示范围重新运行解析、实体、要素、摘要、案卡和报告任务。
6. 记录每批 request ID、源ID、目标ID、成功状态和失败原因。

#### 第五步：导入后处理

1. 运行检索服务的规范化/嵌入生成任务。
2. 记录 embedding 模型名称、版本和生成时间。
3. 只对缺失或模型版本变化的数据生成向量。
4. 验证典型案例表单筛选、相似案例推荐和详情展示。
5. 保存最终迁移清单、失败清单、ID映射和核验结果。

### 13.6 回滚策略

1. 每条迁移数据必须能通过本次导入的 external ID 清单精确识别。
2. 回滚只删除本次新插入且未被正式推荐、收藏或报告引用的数据。
3. 已产生下游引用时，不执行级联删除；停止回滚并人工处理。
4. 删除或批量回滚属于破坏性操作，必须再次获得明确批准。
5. 最终兜底是恢复迁移前本地 PostgreSQL 备份；执行恢复前仍需确认具体数据库目标。

### 13.7 P7 验收条件

- 源、接受、拒绝、冲突和目标数量可闭合。
- 重复运行不会重复插入。
- 所有新增记录有可追踪的来源ID。
- 抽样内容与 SQLite 原文一致。
- 查询、详情和推荐接口均能使用迁移数据。
- 5个演示案件均有明确目标用户和组织，实际文件可下载且哈希一致。
- 演示案件的解析和六类实体由服务器模型重新生成，原文定位抽样正确。
- SQLite 用户、密钥、日志和错误实体结果没有进入 PostgreSQL。

## 14. 演示案件处理结果重建

5个演示案件的基本信息和文件在 P7 中迁移，处理结果按以下顺序重建：

1. 映射 `cases` 到 `case_record`，确认组织、创建人、承办人和状态。
2. 通过正式上传接口写入案卷存储并计算哈希，不直接插入 `evidence_file`。
3. 使用服务器 MinerU 重新解析，不迁移 `parsed_docs`。
4. 使用服务器 LexPro_8B 生成六类实体，不迁移 `entity_results`。
5. 根据演示验收范围重新生成要素、摘要、案卡和报告。
6. 演示用户不迁移；由原 LexPro 已有开发账号承接案件并建立分配关系。

## 16. 风险清单及控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 句内 offset 被当作全文 offset | 高亮错误、人工确认错误 | 块级定位、后端换算、原文严格匹配、hash绑定 |
| Python/Java/JS索引单位不同 | 特殊字符后整体错位 | 合同固定 UTF-16 或统一由Java计算，加入特殊字符测试 |
| MinerU 输出顺序变化 | 全文和定位不稳定 | 保存块顺序、页码、parser版本和text hash |
| 模型服务不可用 | 任务积压或失败 | readiness、超时、并发限制、明确失败，不静默降级 |
| 外部服务泄露案件材料 | 合规风险 | 仅批准内网服务、总开关、脱敏日志、访问控制 |
| SQLite 字段质量不一致 | 导入失败或检索污染 | 预览、映射白名单、拒绝清单、人工抽查 |
| 典型案例重复 | 推荐结果重复 | 稳定 external ID、内容指纹、冲突不覆盖 |
| 直接覆盖新版前端 | 权限和正式流程丢失 | 只迁移视觉/组件，保留Vue路由和API层 |
| Flask接口继续残留 | 出现两套业务口径 | 前端只允许调用 `/api/v1`，构建检查旧路径 |
| V6结构未经批准 | 违反数据库规则 | 将执行V6设为独立审批点 |

## 17. 建议里程碑和交付顺序

工期需要在服务器可用性、页面确认稿和测试数据确定后估算。建议按以下里程碑验收，不用“全部做完后一次验收”：

1. M-A 合同冻结：目标架构、实体合同、页面范围、迁移映射批准。
2. M-B 模型链路：MinerU和LexPro_8B通过非敏感样本真实联调。
3. M-C 实体闭环：上传、解析、识别、高亮、定位、确认、历史完整可用。
4. M-D 案例闭环：新版表单调用原接口，迁移案例可查、可推荐、可收藏。
5. M-E 全量迁移：本地开发库小批验证通过后，完成典型案例和演示案件导入。
6. M-F 系统验收：安全、性能、备份恢复和全流程回归通过。

## 18. 每个阶段的完成定义

一个阶段只有同时满足以下条件才算完成：

1. 代码或脚本已实现且经过评审。
2. 最小必要测试通过。
3. 受影响后端/前端完成构建。
4. API 已验证真实状态码和响应体。
5. 数据库变更已在本地开发库按“小批验证后全量”的顺序验证，且没有修改已应用迁移。
6. 敏感字段未出现在响应和日志中。
7. 手工步骤、环境变量和剩余风险已记录。
8. 对应验收条件有证据，不以“页面能打开”替代业务验收。
